# P2 — OpenUSD 컴포지션 실측 (1차)

NVIDIA `Assembling Digital Twins` 코스가 제공하는 공장 씬을 **읽어서 계측했다.** GPU도 Isaac Sim도 USD Composer도 쓰지 않았다. `usd-core` 하나로 했다.

원자료: [results/p2_composition.csv](../results/p2_composition.csv) · 도구: [scripts/p2_inspect_stage.py](../scripts/p2_inspect_stage.py)

## 환경

| 항목 | 값 |
|---|---|
| usd-core | 26.08 |
| Python | 3.11.15 (`D:\ic\usdenv`, isaacsim env과 분리) |
| 대상 | `PhysicalAI_SceneAssembly_Start/` (1,074MB, 168 files) |
| 설치 시간 | **2초** (venv 생성 포함 10초 미만) |

> Isaac Sim pip 설치는 25분 이상 걸리고 매 세션 초기화된다. 컴포지션은 파일을
> 읽어 합치는 규칙이라 렌더링이 필요 없고, 그래서 이 작업은 그 대기에 묶이지 않는다.

## 1. 페이로드는 무엇을 아끼는가 — 25배

같은 파일을 로드 정책만 바꿔 열었다.

| 정책 | 여는 시간 | 프림 수 | 로드된 페이로드 |
|---|---:|---:|---:|
| `LoadAll` | 5.1 s | 35,812 | 185 |
| `LoadNone` | **0.2 s** | **517** | 0 |

**여는 시간 25배, 프림 수 69배.** 배치만 확인하려면 전체를 열 이유가 없다는 뜻이다.

주의 — 페이로드는 "가벼운 참조"가 아니다. **로드하고 나면 비용이 같다.** 다른 건 안 여는 선택지가 생긴다는 것뿐이다. 위 표의 두 줄은 같은 파일이다.

## 2. 아크 구성 — 두 파일이 전략이 다르다

| | SceneAssembly.usd | CL6_Line_Full.usd |
|---|---:|---:|
| payload | 71,343 | 62,194 |
| reference | 35,811 | **0** |
| specialize | 460 | 345 |

**조립본(`CL6_Line_Full`)은 참조를 하나도 안 쓰고 전부 페이로드로 붙였다.** 라인 하나를 통째로 접었다 폈다 할 수 있게 만든 것이다. 반면 루트 씬은 둘을 섞는다.

`specialize`가 수백 개 나온 것도 눈에 띈다. 가장 약한 아크라 "아무도 안 정했으면 이 값" 용도인데, 머티리얼 기본값에 쓰인 것으로 보인다(미확인).

## 3. ★ 단위가 파일마다 다르다 — 코스 자료 안에 이미 있다

| 파일 | metersPerUnit | 뜻 |
|---|---|---|
| `Assets/Machine_USD/N_02_PCB_Router/N_02_PCB_Router.usd` | **1.0** | 미터 |
| `SceneAssembly.usd` | **0.01** | 센티미터 |
| `Assemblies/CL6_Line_Full.usd` | **0.001** | 밀리미터 |

**한 코스 자료 안에 세 종류가 다 있다.** 기계 에셋(m) → 루트 씬(cm) → 조립본(mm)으로,
가장 멀리 떨어진 두 파일은 **1000배** 차이다.

그리고 NVIDIA는 이걸 자동 생성 서브레이어로 봉합한다 — 에셋을 열 때 이런 경고가 나온다:

```
Could not load sublayer @.../UnitsAdjust-a4ee82beffdaf6ce8f82a9489b46866e.metricsAssembler@
of layer @.../Component/gantry_picker.usd@; skipping.
```

`metricsAssembler`는 **Omniverse Kit 전용 확장**이라 순수 usd-core에는 없다. 그래서 usd-core로 열면 이 보정 레이어가 통째로 빠진다.

이게 두 가지를 말해준다.

1. **단위 불일치는 이론적 위험이 아니라 기본값이다.** NVIDIA 공식 교육 자료조차 섞여 있고, 전용 도구로 봉합한다.
2. **usd-core 접근법의 한계가 정확히 여기다.** 구조 분석·계측은 되지만, **좌표를 신뢰하려면 Kit이 필요하다.** 위치·치수를 다루는 작업은 USD Composer에서 확인해야 한다.

> 코스 문서 페이지에는 워크스페이스 설정을 `0.001`(mm)로 잡으라고 돼 있다.
> 실제 시작 씬은 `0.01`(cm)이다. **문서와 파일이 다르면 파일이 맞다.**

## 4. 인스턴싱이 선언만 되고 작동하지 않는다

| | instanceable 프림 | 프로토타입 |
|---|---:|---:|
| SceneAssembly.usd | 67 | **0** |
| CL6_Line_Full.usd | 0 | 0 |

**67개가 `instanceable=true`인데 프로토타입이 0개다.** 인스턴싱은 프림에 참조·페이로드가 직접 붙어 있어야 프로토타입이 생긴다. 플래그만 켜면 아무 효과가 없다.

35,812개 프림에 인스턴싱이 사실상 0이라는 건, 같은 기계·펜스가 반복될 때 **GPU에서 그 배수로 든다**는 뜻이다. 코스에 `Instancing Best Practices` 모듈이 있는 이유가 이것으로 보인다 — **시작 씬은 일부러 최적화가 안 된 상태다.**

→ 다음 측정: instanceable을 제대로 걸었을 때 프로토타입 수와 메모리가 어떻게 변하는가.

## 5. BIM 메타데이터가 2,105개 프림에 실려 있다

공장 셸(`Factory_Shell_Export/DemoWarehouse`)에 Revit에서 온 IFC 속성이 그대로 남아 있다.

```
BIM:Instance:Category      = 'Curtain Panels'
BIM:Instance:IfcGUID       = '2dobf97CX6YPq_6_YkJeFg'
BIM:Type:OmniClass_Number  = '23.25.20.14.11.11.17'
BIM:Instance:Area          = '9 m2'
```

이게 디지털 트윈이 CAD·BIM 파이프라인의 끝단이라는 증거다. 형상만 온 게 아니라 **건축 자산 정보가 같이 왔다.** 다만 값이 전부 `string`이다 — `Area = '9 m2'`처럼 단위가 문자열에 섞여 있어서 기계가 계산에 쓰려면 파싱이 필요하다.

Blender 잔재(`userProperties:blender:data_name`)와 3ds Max 잔재(`smoothgroups3DSMax`)도 섞여 있다. **에셋이 여러 DCC를 거쳐 왔다는 뜻이고**, SimReady 검증이 필요한 이유이기도 하다.

## 6. 머티리얼도 참조로 붙어 있다 — 99.5%

`N_02_PCB_Router.usd`에서 머티리얼이 바인딩된 프림 **1,881개**의 정의가 어디서 오는지 셌다.

| 정의가 있는 레이어 | 프림 수 | 비율 |
|---|---:|---:|
| `Material.usd` (중앙 라이브러리) | 1,871 | 99.5% |
| `Keyboard.usd` | 9 | |
| **`N_02_PCB_Router.usd` (자기 자신)** | **8** | |
| `Delta.usd` | 1 | |

머티리얼이 기계 파일에 박혀 있지 않고 **중앙 라이브러리를 참조**한다. 라이브러리 한 곳을 고치면 이 머티리얼을 쓰는 에셋 전부에 반영된다 — 코스가 `Centralized Materials Library` 모듈에서 가르치는 것이 이 구조다.

**단, 8개는 예외다.** 자기 파일 안에 직접 정의돼 있다. 중앙 관리 원칙이 100%가 아니라는 뜻이고, 머티리얼을 일괄 교체할 때 **이 8개는 안 바뀐다.**
