# 문서 작성 가이드 — Isaac Sim 학습 문서

## 0. 왜 이 문서가 생겼나

SimReady 정리본을 처음 썼을 때 **읽히지 않았다.** 내용이 틀린 게 아니라
명세의 목차를 그대로 옮겨놨기 때문이다. 이미 아는 사람에게는 잘 정리된 글이고
처음 보는 사람에게는 단어의 나열이었다.

원인은 문체가 아니라 **문서의 종류를 잘못 골랐다**는 것이었다.
그래서 이 가이드의 1장이 문체가 아니라 종류 선택이다.

---

## 1. 먼저 문서 종류를 정한다 ★

글을 쓰기 전에 이 질문에 답한다. **이걸 안 정하면 나머지 규칙이 다 소용없다.**

> 이 문서를 읽는 사람은 **배우려는** 중인가, **일하는** 중인가?

| 종류 | 목적 | 읽는 상황 | 쓰는 방식 |
|---|---|---|---|
| **설명 (Explanation)** | 이해시킨다 | 개념을 처음 만났다 | 문제 상황 → 비유 → 개념. 왜부터 시작 |
| **튜토리얼 (Tutorial)** | 해보게 한다 | 처음 손대본다 | 따라 하면 되는 순서. 결과가 눈에 보이게 |
| **실습 가이드 (How-to)** | 일을 끝내게 한다 | 목적이 분명하다 | 목표별 절차. 설명 최소화 |
| **레퍼런스 (Reference)** | 찾게 한다 | 이미 알고 확인만 한다 | 표·목록·정렬. 서술 금지 |

**판별 요령**

- 독자가 "이게 뭔데?"라고 묻는 상태 → **설명**
- "어떻게 하는데?" → **튜토리얼** 또는 **실습 가이드**
- "그 옵션 값이 뭐였지?" → **레퍼런스**

**섞지 않는다.** 한 문서가 설명과 레퍼런스를 겸하면 둘 다 실패한다.
같이 필요하면 문서를 나누고 서로 링크한다.
제목에 `실습 + 레퍼런스`처럼 두 종류가 들어가 있으면 이미 신호다.

> **레퍼런스에는 이 가이드의 설명형 규칙을 적용하지 않는다.**
> 용어집에 비유를 넣으면 찾기가 느려진다. 레퍼런스는 레퍼런스답게 둔다.

## 2. 맨 앞에 독자와 목적을 밝힌다

설명·튜토리얼 문서는 첫 화면에 이 블록을 넣는다. 네 줄이면 된다.

```
읽는 대상   로봇·시뮬레이션은 다뤄봤지만 SimReady는 처음인 사람
다 읽으면   왜 생겼는지, 프로필 이름을 어떻게 읽는지, 내 작업 어디에 걸리는지
필요 지식   없음. USD·PhysX를 몰라도 읽히도록 씀
분량        약 12분
```

효과가 두 개다. 읽는 사람이 자기 글인지 3초 만에 판단하고,
쓰는 사람이 **수준을 정해놓고 쓰게 된다.** 이 블록 없이 쓰면 글이 중간에 어려워진다.

## 3. 설명형 문서의 뼈대

순서를 지킨다. 특히 **1번을 개념 정의로 시작하지 않는 것**이 핵심이다.

| 절 | 내용 | 주의 |
|---|---|---|
| 1 | **문제 장면** — 뭐가 안 되는지 구체적으로 | 정의로 시작하지 않는다. "서랍이 안 열린다"로 시작 |
| 2 | **그래서 뭐가 필요한가** — 필요한 요소를 낱개로 | 항목마다 "없으면 뭐가 깨지는지"를 붙인다 |
| 3 | **누가 판정하나** — 규칙·명세가 등장할 자리 | 여기서 처음으로 공식 용어를 꺼낸다 |
| 4 | **구조 설명** — 제일 어려운 부분 | 반드시 그림. **왜 이렇게 나눴는지**부터 |
| 5 | **읽는 법 · 고르는 법** | 외우게 하지 말고 규칙으로 읽게 |
| 6 | **내가 이미 해본 것과 연결** ★ | 이 절이 체감 난이도를 제일 크게 낮춘다 |
| 7 | **실제 절차** | 번호 매긴 단계 |
| 8 | **헷갈리기 쉬운 것** | 3개 내외 |
| 9 | **한 장 요약** | 다 읽고 남길 것만 |
| 10 | **출처** | 날짜·버전 명시 |

**6번을 빼먹지 않는다.** 새 개념을 배우는 게 아니라
**이미 아는 문제에 이름이 붙는 구조**로 만들면 흡수 속도가 다르다.
현장 증상 ↔ 명세 용어를 2열 표로 짝지어 놓는 게 가장 잘 먹힌다.

## 4. 문체 — 번역투 제거

### 기본

- **합니다체**로 통일한다. 설명형에서 `~한다`체는 논문투로 읽혀 거리감이 생긴다
  (프로젝트 README·로그는 `~한다`체 유지. 성격이 다르다)
- 한 문장에 주장 하나. 길어지면 자른다
- 문단은 3~5줄. 그 이상이면 나눈다

### 고칠 패턴

| 하지 말 것 | 대신 |
|---|---|
| `~하는 것이다` / `~라는 것` | 서술어로 끝낸다 |
| 명사 나열 — "기계 검증 규칙 포함" | 동사로 푼다 — "기계가 검사할 수 있게 코드로 적어둡니다" |
| `~에 대해` / `~에 의해` | 조사를 바꾸거나 능동으로 |
| 피동 — "정의되어 있습니다" | 능동 — "정의합니다" / "적어둡니다" |
| 괄호 안 원어 남발 | 처음 1회만. 이후 한국어 |
| 줄표(—) 과다 | 문단당 1개 이하 |
| 영어 어순 직역 | 한국어 어순으로 다시 쓴다 |

### 예시

> ✗ SimReady는 시뮬레이션용 3D 콘텐츠가 충족해야 할 조건을 정의하는 개방형 명세로서,
> 검증 규칙과 기능 어댑터를 제공하는 것이 주요 기능이다.
>
> ✓ SimReady가 하는 일은 두 가지입니다. 에셋이 조건을 만족하는지 **검사**하고,
> 한 형식을 다른 형식으로 **변환**합니다.

## 5. 비유 사용법

**낯선 개념 하나에 비유 하나.** 없으면 만들지 말고, 억지 비유는 오히려 방해된다.

- **본문과 시각적으로 분리한다.** 별도 상자 + `비유` 라벨.
  섞어 쓰면 비유가 사실로 읽힌다
- 독자가 확실히 아는 것에서 가져온다. 자동차, 사진, 검사, 도구
- 비유는 **구조**를 옮기는 것이지 결론을 대신하지 않는다.
  비유 뒤에 반드시 원래 용어로 돌아온다
- 문서 끝에 한 줄 — "비유는 이해를 돕는 장치이므로 정확한 조건은 원문 확인"

검증된 비유 예시:

| 개념 | 비유 |
|---|---|
| 형상만 있는 3D vs 물리가 있는 3D | 자동차 사진 vs 실제 자동차 |
| SimReady 적용 전후 | 인형 vs 로봇 장난감 |
| 요구사항→기능→피처→프로필 | 자동차 검사 항목 → 분야 → 검사 세트 → 검사 코스 |
| 중립 프로필과 어댑터 | 사진 원본과 용도별 내보내기 |

## 6. 그림 — 언제 그리고 어떻게 그리나

### 그릴 가치가 있는가

**문장으로 더 빠르면 문장으로 쓴다.** 그림이 필요한 경우는 세 가지뿐이다.

1. **흐름** — 무엇이 무엇으로 변하는가 (변환 파이프라인, 데이터 이동)
2. **비교** — 두 방식의 차이. 반드시 **차이 자체**를 그린다.
   선택지를 나란히 나열만 하는 건 비교가 아니다
3. **구조** — 층위·포함 관계. 단, 이름만 적은 상자는 그리지 않는다

박스에 이름만 써 넣은 그림은 본문보다 정보가 적다. 그런 그림은 지운다.

### 인라인 SVG 규격

```
viewBox      내용에 맞춰 직접 정한다. 가로 흐름은 넓게, 층위는 세로로
크기         CSS로 width:100%; height:auto
색           stroke·text 는 currentColor → 라이트/다크 자동 대응
강조색       의미를 가진 요소 하나에만 리터럴 색. #0E9AA8 (양쪽 테마에서 읽힘)
화살표       <defs><marker> + <polygon>. 이미지 금지
글자         원본 11~13px, 축소 배율 고려. 짧은 라벨만
접근성       <figure> + <figcaption>, svg에 role="img" + aria-label
금지         <script> <style> <foreignObject> 내부 삽입
```

**화살표에 라벨을 붙인다.** 이름 없는 화살표는 "관련 있음"이라는 뜻밖에 못 준다.
`검사`, `변환`, `어느 피처에서 걸렸나`처럼 적는다.

### 흔한 실패 두 가지

**① 가로로 너무 길어서 글자가 작아진다.**
컨테이너 폭보다 viewBox가 넓으면 축소되고 글자도 같이 작아진다.
상자 5개를 가로로 늘어놓으면 대개 여기 걸린다.
→ **세로 배치로 바꾼다.** "좁혀 들어간다"는 의미와도 대개 더 맞는다.

**② 화살표 라벨이 상자와 겹친다.**
상자 사이 간격보다 라벨이 길면 겹친다. 렌더링해서 눈으로 확인하기 전엔 모른다.
→ 간격을 넓히거나, 세로 배치로 바꿔 라벨을 화살표 옆에 둔다.

## 7. 시각 규격

본문 줄길이와 폰트가 가독성의 절반이다.

```
줄길이     --measure: 40rem   ← ch 단위 쓰지 말 것
```

> **`ch`는 숫자 `0`의 폭 기준이라 한글에 맞지 않는다.**
> `64ch`가 실제로는 한글 30자 남짓이다. rem으로 직접 잡는다.
> 한 줄에 한글 40자 안팎이 읽기 좋다.

```
폰트       본문 "Malgun Gothic" (이 PC에 있는 유일한 한글 폰트)
           코드·ID  ui-monospace, Consolas, D2Coding
           웹폰트 링크 금지 — 아티팩트 CSP가 막는다. 조용히 폴백됨
본문크기    17px / 행간 1.85   ← 한글은 라틴보다 행간을 넉넉히
전체폭      wrap 66~73rem. 본문은 --measure가 잡으므로 넓혀도 안 길어진다
그림·표     본문보다 넓게 써도 된다. 편집 디자인의 정상 패턴
테마        :root 토큰 → @media(prefers-color-scheme) → [data-theme] 순서로 3벌
```

**긴 표는 `overflow-x:auto` 컨테이너 안에 둔다.** 페이지 본체가 가로로
밀리면 안 되고, 표만 자체 스크롤되게 한다.

### CSS 캐스케이드 주의

같은 특정도의 선언은 **뒤에 온 것이 이긴다.** 실제로 당한 사고:

```css
@media (min-width: 1080px) { .rail { display: block; } }
.rail { display: none; }        /* ← 뒤에 있어서 데스크톱에서도 숨겨짐 */
```

레일이 사라지면서 그리드의 첫 칸이 비었고, `main`이 12rem짜리 좁은 칸으로
밀려 들어가 본문이 208px 폭에 갇혔다. **모바일 우선 선언을 미디어쿼리보다 앞에 둔다.**

## 8. 정직성 규칙

- 시뮬레이션에서 나온 수치는 **`(시뮬 기준)`** 표기. 실기 검증 안 한 값을 실측처럼 쓰지 않는다
- **측정하지 않은 데이터점을 그리지 않는다.** 주파수 스캔이 3점이면 3점이다
- 팀 작업은 역할 범위를 밝힌다
- 출처와 조회 날짜, 문서 버전을 남긴다
- 문서 끝에 한 줄 — **"원문과 다르면 원문이 맞습니다"**
- 실패는 실패로 적는다. 실패 진단도 내용이다

## 9. 다 쓰고 나면 반드시 렌더링해서 본다

**코드만 보고 끝내지 않는다.** 겹침·잘림·축소는 렌더링해야 보인다.
이 PC에서 확인하는 방법:

미리보기 파일 만들기 (아티팩트는 `<!doctype>` 없이 쓰므로 감싸준다):

```powershell
$sp = "<스크래치패드 경로>"
$body = Get-Content "$sp\문서.html" -Raw -Encoding UTF8
$html = "<!doctype html><html lang=`"ko`"><head><meta charset=`"utf-8`"><meta name=`"viewport`" content=`"width=device-width,initial-scale=1`"></head><body>" + $body + "</body></html>"
[System.IO.File]::WriteAllText("$sp\preview.html", $html, [System.Text.Encoding]::UTF8)
```

전체 페이지 스크린샷:

```powershell
& "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --headless=new --disable-gpu --hide-scrollbars --window-size=1500,4600 --screenshot="$sp\shot.png" "file:///$($sp -replace '\\','/')/preview.html"
```

그림 하나만 잘라서 확대 확인 (ffmpeg):

```powershell
& "<ffmpeg 경로>\ffmpeg.exe" -y -i "$sp\shot.png" -vf "crop=1000:760:400:3600" "$sp\fig.png"
```

> **함정**: Edge 헤드리스는 Windows 최소 창 너비 때문에 `--window-size=430`을 줘도
> 실제로는 492px로 렌더하고 스크린샷만 430px로 자른다.
> 좁은 폭에서 글자가 잘려 보이면 **레이아웃 버그가 아니라 이 현상일 수 있다.**
> 실제 폭이 궁금하면 페이지에 측정 스크립트를 넣고
> `document.documentElement.scrollWidth`와 `window.innerWidth`를 비교한다.

## 10. 최종 체크리스트

**종류와 독자**
- [ ] 문서 종류를 하나로 정했다 (설명/튜토리얼/실습/레퍼런스)
- [ ] 맨 앞에 읽는 대상·얻는 것·필요 지식·분량을 밝혔다
- [ ] 개념 정의가 아니라 문제 장면으로 시작한다

**내용**
- [ ] 낯선 개념마다 비유가 있고, 비유는 상자로 분리돼 있다
- [ ] "이미 해본 것과 연결" 절이 있다
- [ ] 한 장 요약이 있다
- [ ] 헷갈리기 쉬운 것을 따로 모았다

**문체**
- [ ] 합니다체로 통일
- [ ] `~하는 것이다`, 명사 나열, 피동을 걷어냈다
- [ ] 문단이 5줄을 넘지 않는다

**그림**
- [ ] 모든 그림이 문장보다 빠르게 설명한다
- [ ] 화살표에 라벨이 있다
- [ ] currentColor를 쓰고 강조색은 하나뿐이다
- [ ] figcaption이 그림의 주장을 한 문장으로 말한다

**시각**
- [ ] 줄길이를 rem으로 잡았다 (ch 아님)
- [ ] 라이트/다크 둘 다 확인했다
- [ ] 넓은 표가 자체 스크롤된다

**검수**
- [ ] 렌더링해서 눈으로 확인했다
- [ ] 그림을 확대해 겹침·잘림을 확인했다
- [ ] 출처·날짜·버전이 있고 "원문이 맞습니다" 문장이 있다
